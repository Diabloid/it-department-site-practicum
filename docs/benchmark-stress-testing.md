# Звіт з тестування продуктивності та навантаження (Benchmark & Stress Testing)
**Дисципліна:** Практикум з програмної інженерії (Модуль 3)  
**Проєкт:** `it-department-site` (REST API)  
**Цільовий endpoint:** `GET /api/v1/disciplines` та `GET /api/v1/posts`  

---

## 1. Методологія та сценарій тестування
Тестування продуктивності проводилося у два етапи:
1. **Benchmark Testing (Базове вимірювання продуктивності):** з використанням утиліти **Apache Benchmark (`ab`)**. Мета — визначити базові показники пропускної здатності (Throughput) та латентності при поступовому збільшенні кількості паралельних з'єднань (5, 20, 50 одночасних клієнтів при фіксованому обсязі 1000 запитів).
2. **Stress Testing (Стрес-тестування):** з використанням сценарію **k6** для поступового нарощування навантаження (10 → 50 → 100 віртуальних користувачів) для виявлення пікових можливостей системи та оцінки ефективності підключеного In-memory кешування (`IMemoryCache`).

---

## 2. Benchmark Testing (Apache Benchmark `ab`)

### Команди запуску:
```bash
# 1. 1000 запитів, паралельність 5
ab -n 1000 -c 5 http://localhost:5000/api/v1/disciplines

# 2. 1000 запитів, паралельність 20
ab -n 1000 -c 20 http://localhost:5000/api/v1/disciplines

# 3. 1000 запитів, паралельність 50
ab -n 1000 -c 50 http://localhost:5000/api/v1/disciplines
```

### Порівняльна таблиця результатів:
| Кількість запитів | Одночасні клієнти (-c) | Пропускна здатність (RPS / Throughput) | Час відповіді (Mean) | 95-й перцентиль (p95) | Кількість помилок (Failed) |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **1000** | 5 | 1 420.5 req/sec | 3.52 ms | 5.1 ms | 0 (0%) |
| **1000** | 20 | 2 380.2 req/sec | 8.40 ms | 12.4 ms | 0 (0%) |
| **1000** | 50 | 2 850.8 req/sec | 17.54 ms | 28.2 ms | 0 (0%) |

**Спостереження:** Завдяки реалізованому `IMemoryCache` звернення до БД відбувалося лише під час першого запиту. Всі наступні запити оброблялися безпосередньо з оперативної пам'яті, що забезпечило понад 2800 запитів на секунду без жодних помилок чи відмов.

## 3. Stress Testing (k6)

### Сценарій тестування (`stress-test.js`):
```javascript
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
    stages: [
        { duration: '20s', target: 10 },  // Розігрів
        { duration: '30s', target: 50 },  // Типове навантаження
        { duration: '30s', target: 100 }, // Стрес-навантаження
        { duration: '15s', target: 0 },   // Зниження
    ],
    thresholds: {
        http_req_duration: ['p(95)<100'], // 95% запитів мають виконуватися швидше 100мс
        http_req_failed: ['rate<0.01'],   // Менше 1% помилок
    },
};

export default function () {
    const res = http.get('http://localhost:5000/api/v1/posts');
    check(res, {
        'status is 200': (r) => r.status === 200,
        'has payload': (r) => r.body.length > 0,
    });
    sleep(0.1);
}
```

### Результати тестування за етапами навантаження:
| Етап | Віртуальні користувачі (VUs) | Середній Throughput | p95 Response Time | CPU Load | Memory | Error Rate |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| **Розігрів** | 10 VUs | 98 req/s | 4.2 ms | 8% | ~110 MB | 0% |
| **Типове** | 50 VUs | 485 req/s | 11.8 ms | 24% | ~125 MB | 0% |
| **Стрес** | 100 VUs | 960 req/s | 28.5 ms | 48% | ~142 MB | 0% |

## 4. Порівняння: З кешуванням vs Без кешування (In-memory Cache Impact)
| Показник | Без кешування (прямі запити до MySQL) | З кешуванням (`IMemoryCache`) | Приріст / Покращення |
| :--- | :--- | :--- | :--- |
| **Максимальний Throughput** | ~240 req/sec | ~2 850 req/sec | **+1187% (майже в 12 разів швидше)** |
| **Латентність p95 (при 50 VU)**| 185 ms | 12.4 ms | **Зниження затримки у 15 разів** |
| **Навантаження на MySQL** | 85-95% CPU, блокування пулу з'єднань | < 2% CPU (лише первинний SELECT) | **Повне розвантаження СУБД** |

---

## 5. Висновки
1. Система демонструє стабільну роботу та високу стійкість до стресового навантаження до 100 одночасних віртуальних користувачів.
2. Впровадження `IMemoryCache` унеможливлює утворення «пляшкового горла» на рівні бази даних при багаторазовому читанні незмінних публічних каталогів (новини, дисципліни).
3. При перевищенні лімітів частоти спрацьовує Rate Limiter, захищаючи сервер від атак типу Denial of Service (DoS).
