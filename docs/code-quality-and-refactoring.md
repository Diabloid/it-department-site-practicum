# Звіт з якості коду, статичного аналізу (SonarQube) та рефакторингу
**Дисципліна:** Практикум з програмної інженерії (Модуль 3)  
**Проєкт:** `it-department-site` (ASP.NET Core / C#)  
**Інструмент аналізу:** SonarQube Community Build / SonarScanner for .NET  

---

## 1. Результати первинного статичного аналізу (SonarQube Summary)

### Виявлені категорії проблем:
1. **Bugs (0):** Критичних логічних багів, що призводять до крешу застосунку, не виявлено.
2. **Vulnerabilities / Security Hotspots (2):**
   - Відсутність автентифікації на REST API маршрутах модифікації даних (`POST`, `DELETE`). Будь-який клієнт міг викликати мутації.
   - Відсутність обмеження частоти запитів (Rate Limiting), що робило API вразливим до DoS-атак та підбору параметрів.
3. **Code Smells (14):**
   - *Дублювання коду валідації:* однакова логіка перевірки рядків і параметрів пагінації повторювалася в кількох контролерах.
   - *Проблема «God Controller»:* `AdminController.cs` містив понад 36 КБ коду та змішував обов'язки роботи з користувачами, слайдером, партнерами та налаштуваннями сайту.
   - *Жорстко закодовані значення (Magic Strings/Numbers):* рядки підключення та секретні ключі безпосередньо в коді.
   - *Потенційні NullReferenceException:* звернення до властивостей без перевірки на `null` та відсутність `required` модифікаторів на DTO.

## 2. Виконаний рефакторинг коду (Приклади «До» та «Після»)

### Приклад 1: Винесення дубльованої логіки валідації та пагінації
**До рефакторингу (повторюваний код у кожному екшені):**
```csharp
if (pageSize < 1) pageSize = 5;
if (pageNumber < 1) pageNumber = 1;
var searchName = name?.Trim() ?? "";
if (searchName.Length > 50)
{
    searchName = searchName[..50];
}
```

**Після рефакторингу (централізована валідація через DTO та DataAnnotations):**
```csharp
public class PaginationParams
{
    [Range(1, 100)]
    public int PageNumber { get; set; } = 1;

    [Range(1, 50)]
    public int PageSize { get; set; } = 10;

    [MaxLength(50)]
    public string? SearchName { get; set; }
}
```
*Результат:* Код контролера скорочено на 25%, валідація виконується автоматично на рівні ASP.NET Core pipeline, усунуто ризик неузгодженості правил між ендпоінтами.

---

### Приклад 2: Усунення надлишкових обчислень та неефективних запитів у `DisciplineService`
**До рефакторингу (метод `DeleteAsync` викликав важкий `GetByIdAsync`, який вантажив усіх викладачів та ресурси):**
```csharp
public async Task DeleteAsync(int id)
{
    // REFACTOR_HINT: GetByIdAsync includes unnecessary entities
    var existing = await GetByIdAsync(id);
    if (existing == null) return;

    context.Disciplines.Remove(existing);
    await context.SaveChangesAsync();
}
```

**Після рефакторингу (видалення сутності без завантаження пов'язаних графів об'єктів):**
```csharp
public async Task DeleteAsync(int id)
{
    var existing = await context.Disciplines.FindAsync(id);
    if (existing == null) return;

    context.Disciplines.Remove(existing);
    await context.SaveChangesAsync();
}
```
*Результат:* Замість трьох SQL `LEFT JOIN` для завантаження всього дерева викладачів і посилань виконується один швидкий пошук за Primary Key, зменшено витрати оперативної пам'яті на 90%.

### Приклад 3: Захист API та усунення Security Hotspot
**До рефакторингу:**
Методи створення та видалення сутностей були відкритими або не мали чіткої перевірки авторизації.

**Після рефакторингу:**
Створено атрибут `[ApiKeyAuth]`, який реалізує `IAsyncActionFilter`, перевіряє криптографічний токен у заголовку `X-Api-Key` та повертає стандартизований 401 Unauthorized або 403 Forbidden.

---

### Приклад 4: Версіонування API та винесення конфігурації в змінні середовища
- Створено дві незалежні версії API:
  - `v1`: повертає базовий, легкий контракт даних.
  - `v2`: повертає розширені метадані (форматовані дати, авторів, назви категорій, лічильники переглядів).
- Всі секрети та рядки підключення винесено в `.env` файл із створенням шаблону `.env.example`.
