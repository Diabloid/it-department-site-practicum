# Звіт з профілювання бекенд-застосунку (Profiling Report)
**Дисципліна:** Практикум з програмної інженерії (Модуль 3)  
**Проєкт:** `it-department-site` (ASP.NET Core / .NET 10)  
**Інструменти:** Visual Studio Diagnostic Tools, `dotnet-trace`, `dotnet-counters`  

---

## 1. Сценарій профілювання
Профілювання виконувалося в режимі навантаження під час виконання двох ключових сценаріїв:
1. Масове завантаження списку публікацій із категоріями та авторами (`GET /api/v2/posts`).
2. Отримання дисциплін із пагінацією та пошуком за назвою (`GET /disciplines/paged?pageNumber=1&pageSize=10`).

---

## 2. Виявлені вузькі місця (Bottlenecks) до оптимізації

### Проблема 1: Проблема N+1 запитів в Entity Framework Core
- **Симптом:** При вибірці списку сутностей, що мають зв'язки (наприклад, `Post` з `Categories` та `Author`, або `Discipline` з `Employees`), ORM генерувала окремий SQL-запит для кожного дочірнього елемента в циклі серіалізації.
- **Вплив:** На 20 постів виконувалося 41 звернення до бази даних (1 основний SELECT + 20 для категорій + 20 для авторів), що призводило до різкого зростання затримки (до 240 мс).

### Проблема 2: Надлишковий трекінг сутностей (`ChangeTracker`) при операціях читання
- **Симптом:** За замовчуванням Entity Framework створює знімки (snapshots) усіх витягнутих з бази об'єктів для відстеження їхніх майбутніх змін.
- **Вплив:** Підвищене споживання оперативної пам'яті (Allocation Rate ~8.5 MB/sec) та додаткове навантаження на Garbage Collector (Gen 0/Gen 1).

---

## 3. Виконані оптимізації коду

### Оптимізація 1: Eager Loading через `.Include()`
Використано жадібне завантаження пов'язаних таблиць через єдиний оптимізований SQL `JOIN`:
```csharp
// Було: ліниве або роздільне довантаження
var posts = await _dbContext.Posts.ToListAsync();

// Стало: єдиний JOIN-запит через Include
var posts = await _dbContext.Posts
    .Include(p => p.Categories)
    .Include(p => p.Author)
    .Where(p => p.Status == PostStatus.Published)
    .ToListAsync();
```

### Оптимізація 2: Примусове вимкнення трекінгу через `.AsNoTracking()`
Для всіх read-only запитів додано метод `.AsNoTracking()`:
```csharp
var disciplines = await _dbContext.Disciplines
    .AsNoTracking()
    .OrderBy(d => d.SortOrder)
    .ToListAsync();
```

### Оптимізація 3: Кешування вибірок у пам'яті (`IMemoryCache`)
Результати важких вибірок кешуються на 5 хвилин із ковзним терміном (sliding expiration 2 хв), виключаючи повторні запити до СУБД.

## 4. Порівняння метрик: До vs Після оптимізації
| Метрика | До оптимізації | Після оптимізації | Покращення |
| :--- | :--- | :--- | :--- |
| **Кількість SQL-запитів на сторінку** | 41 запит | 1 запит (або 0 при кеші) | **-97.5%** |
| **Виділення пам'яті (Heap Allocations)** | 14.2 MB на 100 req | 1.8 MB на 100 req | **Зменшення на 87%** |
| **Час відповіді ендпоінта (Avg)** | 145 ms | 12 ms | **Прискорення в 12 разів** |
| **Частота збору сміття (GC Gen 0)** | 18 разів / хв | 2 рази / хв | **Зниження навантаження на CPU** |

---

## 5. Висновок
Застосування `.AsNoTracking()`, усунення проблеми N+1 через `.Include()` та впровадження `IMemoryCache` кардинально скоротили витрати CPU та пам'яті, забезпечивши стабільну та швидку роботу сервісу навіть при високому паралельному навантаженні.
